# Feishu：OpenClaw 飞书通道

本仓库维护的官方 Feishu 衍生版，插件 ID 为 `feishu-conversation`，通道 ID 仍为 `feishu`。支持飞书/Lark 消息、群历史与引用上下文、接话窗口、工作卡片、后台结果及本地报告转飞书文档。上游来源见 [UPSTREAM.md](https://github.com/Lydanne/agent-plugins/blob/main/UPSTREAM.md)。

工作卡启用并实际接管本轮回复时，通过公开 `sourceReplyDeliveryMode: automatic` 请求宿主把最终回复交给卡片，兼容默认使用消息工具交付的新版宿主，避免正常结束后误报“未产生可展示的结果”。未创建工作卡的回合保留宿主回复模式；此选项不改变发送权限、撤回和后台任务规则。

## 安装与首次接入

从本仓库构建打包后使用 `openclaw plugins install /absolute/<feishu-package>.tgz`。不要使用 `openclaw plugins install @openclaw/feishu` 来安装此衍生版。完整构建、隔离安装、配置补丁及验收流程见 [OpenClaw 接入指南](https://github.com/Lydanne/agent-plugins/blob/main/docs/openclaw-setup.md)。

在飞书开发者后台创建企业自建应用、启用机器人，按照 [官方 Feishu 接入说明](https://docs.openclaw.ai/channels/feishu) 配置消息权限、事件订阅及应用可用范围，并发布版本。使用 WebSocket 时选择长连接接收事件；需要连续接话或历史读取时，应用还须有接收非 @ 群消息及相应历史读取权限。交互问题须配置卡片回调，文档交付须开通文档创建、编辑、文件上传及授权所需能力。权限名称及审核状态以当前飞书后台为准，不要为普通聊天一次性开启全部文档权限。

### CLI、动态技能与自动更新

插件启用且已有可用飞书应用配置后，在后台安装官方 `@larksuite/cli`，从其内置技能生成轻量索引。首次安装不依赖 npm 生命周期脚本，也不修改机器全局 CLI 或 `~/.agents/skills`。单独安装插件 tarball 尚不代表 CLI 已就绪；查看 `openclaw feishu-cli status`，离线环境可稍后执行 `update` 重试。目录位于宿主状态目录的 `feishu-cli/`，与插件代码分离；不写入插件安装目录或角色仓库。

```json
{
  "channels": {
    "feishu": {
      "cli": {
        "enabled": true,
        "autoUpdate": true,
        "updateCheckIntervalHours": 24,
        "userAuth": false
      }
    }
  }
}
```

`enabled`、`autoUpdate` 默认 true，检查间隔默认 24 小时；关闭自动更新仍进行首次安装，并保留手动更新。`enabled=false` 关闭后台服务、动态目录注入和调用工具。变更更新策略后重启/重新加载插件以重建定时器。可选 `version` 为明确的稳定版本号，例如 `1.0.96`，设置后自动与手动更新均以该版本为目标；不设置则选择 npm 稳定标签。当前集成验证范围为 >=1.0.96 的 1.x，2.x 不自动升级。

```sh
openclaw feishu-cli status
openclaw feishu-cli check
openclaw feishu-cli update
openclaw feishu-cli rollback
```

更新器在独立目录安装指定版本的 npm 包（依赖脚本禁用），显式执行该版本官方二进制安装器（含上游校验），验证程序版本及全部技能可枚举、可读取，再一起切换 CLI 与索引。失败记录状态并保留原版本。`update` 对相同版本也核验并修复索引；`rollback` 恢复上一版本，并至少等待下个检查周期再自动更新。已开始的调用固定使用捕获的版本目录。历史版本目录暂不自动清理，管理员应关注磁盘占用；不要删除仍被任务使用的版本。进程异常中止遗留 `update.lock` 时先确认没有安装进程，再清理这个锁目录重试。

Main 在可信飞书会话获取当前技能目录，并通过 `feishu_cli` 列举、读取技能或执行类型化业务命令。上游技能正文与 references 始终读取同版本 CLI 的内置内容；scripts/assets 不在内置内容中，不承诺这些资源可执行。`apps` 部署、常驻事件、原始 API、本地文件输入输出不开放给此入口，沿用相应现有工具。与旧 `feishu-doc/drive/wiki/perm` 重叠时，已有工具继续服务原流程，CLI 操作先读 `feishu-cli` 接入规则；消息、群历史、卡片、后台交付由原插件能力负责。

应用凭证仅从可信消息账号的运行时配置解析（包括已解析的 SecretRef）。插件通过公开认证接口换取应用访问 Token，在内存中按应用、品牌和凭证版本缓存并合并并发换发，提前续期，再通过子进程环境提供给 CLI；不依赖 CLI 以 App Secret 自动换发 Token。清除操作员 CLI profile/token/sidecar 环境，不写入 CLI profile。业务命令无法选择其他账号、改变身份策略或管理凭证；风险操作保留 CLI 的 exit 10 确认流程。当前仅支持标准 feishu/lark 域名，自定义 API 域名不接入 CLI。

个人资源由管理员显式开启 `userAuth`，并由每位请求人通过 `feishu_cli_auth` 按 scope 授权。插件使用与 CLI 相同的公开 OAuth device flow，单次检查有截止时间；先展示链接与二维码，后续再完成授权。完成及刷新时核对真实 user_info.open_id，拒绝他人扫码；本地状态按账号、App ID、品牌和请求人隔离。授权文件目录 0700、文件 0600，包含运行时 token，须按私有凭证管理，不能提交或分享。只支持 Bearer token；服务端要求 DPoP 时明确失败，不降级绕过要求。退出只删除本地状态，不撤销服务端授权。

Worker 可在原任务授权及自身已有权限内直接使用 Feishu CLI、读取可访问的技能和使用独立登录态。调用 OpenClaw 插件能力（包括 `feishu_cli` 和 `feishu_cli_auth`）时，沿用原任务 `request → awaiting_main → Main 调用 → reply → Worker 恢复`；插件内部认证状态不发送给 Worker。此边界属于执行协议，不能把提示规则描述为操作系统沙箱隔离。

### 消息上下文与字段扩展

`feishu-context` 随插件交付，解释人员、偏好、部门风格、提及、历史和任务来源。消息携带本轮 JSON 数据；`before_prompt_build` 按可信飞书渠道每轮补充 `feishu-context/v3` 的短权限与来源边界，压缩后也重新生效，不依赖 AgentRepo 或 Ada 角色文件。历史原文、读取状态、引用链缺口和摘要统一放在 `[GroupChatHistory]` 的对象中，读取兼容旧数组；当前人员、部门配置与任务来源仍是独立数据段。未知可选字段在历史合并、去重和摘要时保留，完整字段解释见技能引用。

群会话每轮自动携带 `GroupInfo`，包含当前群名称、描述、账号/群标识和读取状态，供 Agent 理解群用途及默认约定；当前请求优先，群描述不扩大权限。沿用读取群资料的接口，一次获取名称和描述，按账号和群隔离缓存 5 分钟，更新群资料后最迟缓存到期刷新。读取失败明确标记 unavailable，不中断消息处理；私聊不读取、不注入群资料。

群资料同时包含群公告（新版 docx 块与旧版 doc）及最多 20 条 Pin 消息的可读正文。公告最多读取 3 页、12,000 字符，每条 Pin 最多 2,000 字符；分页未完、正文读取失败或截断均明确标记，不能称完整读取。仅提供文字投影，图片、附件和链接目标未读取。Pin 正文按当前账号群读取策略、`tools.chat` 和群历史发送者可见范围过滤。公告保留文字超链接的地址但不读取目标页面；在共享 6 秒读取预算内，单条 Pin 或后续公告页失败保留已读部分。失败只携带安全的错误码、原因、是否可重试及已知权限，不输出原始 SDK 请求/错误。读取中或准备上下文期间已失效的快照在派发前移除旧正文，不自动重放读取。

公告和 Pin 在有群对话时按 5 分钟缓存自动刷新，没有后台定时轮询。收到已订阅的 `im.chat.updated_v1` 群资料变更事件会清除当前账号该群的名称、描述及公告/Pin 缓存，下次对话重新读取；消息撤回、机器人退出群也清除相关缓存。当前 SDK 没有公告和 Pin 的专用变更事件处理入口，因此不承诺这两项修改后即时刷新；不会因资料变化启动任务或发送通知。部署时如需群资料事件刷新，应在飞书应用事件订阅中启用“群配置修改”（`im.chat.updated_v1`）；代码注册不会自动修改应用权限或订阅。

字段表及兼容规则见 [上下文技能](skills/feishu-context/SKILL.md) 与 [字段参考](skills/feishu-context/references/fields.md)。新字段通过统一 JSON 数据段按需添加，可选模块扩展使用 `extensions.<模块名>`；固定语义只维护在技能中。保留 false、0、null 及嵌套对象，未知字段不作为指令或权限；破坏性改动须更新协议版本。原始消息、引用关系、来源版本、原生媒体及后端授权/撤回校验保持原有合同。

### 撤回与 Worker 取消

收到可信撤回事件时，飞书插件在同一 SQLite 事务中保存撤回记录和 Worker 待投递事件，再停止当前来源轮次并调用 Worker 的通用来源撤销接口。Worker 未加载或投递失败时保留待投递记录，独立服务启动及之后每秒按最多 100 条重试；稳定事件 ID 支持重复投递，只有 Worker 确认接收才标记已送达。已有历史撤回在首次迁移时进入待投递记录。只保存消息来源标识，不复制消息正文或凭证。

Worker 独立保存撤销记录并控制执行，飞书不操作其进程或任务文件；Worker 不通过飞书来源/交付校验轮询撤回。上述机制以宿主实际收到撤回为前提，未到达的事件无法推断。普通追加来源不会撤销已提交 Worker 的依赖快照；部分来源撤回后的新版本只使用剩余有效来源，交付时仍检查版本、身份和实际来源。撤销接收确认不等于进程已停止，也不表示外部操作已回滚。

### WebUI 二维码接入

扫码向导通过宿主提示页展示不含 ANSI 控制符的等宽二维码及授权 URL（补齐宿主行距产生的码点间隙），不再把二维码仅打印到 Gateway 日志。先用飞书扫码并确认，再点击“继续”验证；尚未授权会再次展示二维码，不在页面背后持续轮询。二维码有效期从获取时起计算，停留页面不会延长有效期。

扫码页可取消或关闭，下一次验证不会继续执行；正在进行的网络请求最多等待 10 秒截止。拒绝、过期、超时、获取二维码失败及网络异常均显示明确提示，再提供手动凭据入口。扫码结果采用前重新核验宿主写入授权；取消不会写入渠道配置，也不会撤销用户已在飞书端确认创建的应用。此流程兼容当前公开 SDK，未修改宿主 WebUI；不是扫码后自动跳转。

最小单账号片段（合入现有配置）：

```json
{
  "plugins": {
    "entries": {
      "feishu": { "enabled": false },
      "feishu-conversation": { "enabled": true, "hooks": { "allowConversationAccess": true } }
    }
  },
  "channels": {
    "feishu": {
      "enabled": true,
      "appId": "cli_REPLACE_ME",
      "appSecret": "REPLACE_WITH_PRIVATE_SECRET_OR_SECRET_REF",
      "domain": "feishu",
      "connectionMode": "websocket",
      "dmPolicy": "pairing",
      "groupPolicy": "allowlist",
      "groupAllowFrom": ["oc_REPLACE_WITH_TEST_CHAT_ID"],
      "requireMention": true,
      "documentDelivery": { "enabled": false }
    }
  }
}
```

示例凭证仅是占位符，真实值存放在宿主私有配置或支持的 SecretRef 中。同一 Gateway 只能启用一个飞书实现。`groupAllowFrom` 控制群准入；具体群的 `groups.<chatId>.allowFrom` 控制该群发送者。绑定到特定 Agent 时，使用宿主原生渠道 bindings；账号键、Agent ID 和群 ID 须与实际配置一致。Lark 使用 `domain="lark"`，自定义域名见 schema。

最小配置未登记 workspaceSync，因此不执行旧工作区同步；已有部署关闭旧同步时只补 enabled=false 并保留其 root 等字段。先验收普通 @ 回复，再依次开启窗口、工作卡片和报告功能，便于定位权限及交付问题。多账号使用 `channels.feishu.accounts.<accountId>`，按需指定 defaultAccount；共享字段可在账号覆盖，数组整体替换。

## 用户怎样使用

| 操作 | 用户看到的行为 | 管理员需准备 |
| --- | --- | --- |
| 群里 @机器人＋具体问题 | 进入所绑定 OpenClaw 主会话 | 群/发送者准入、机器人与消息事件 |
| 只 @机器人 | 返回 mentionGreeting 或通用问候 | 可配置实际能力介绍 |
| @ 后连续补充信息 | 有效窗口内判定是否继续接话 | conversationWindow、非 @ 消息权限 |
| 引用旧消息并 @ | 主会话获得引用链与历史参考 | 历史读取权限及历史策略 |
| 对原任务补充、更正或询问进度 | 按来源、任务修订和当前工作状态处理 | 保持原消息/任务关联；见下文命令配置 |
| 提交耗时任务 | 工作卡显示受理和进度，完成后交付 | agent-worker、asyncCompletion、工作卡设置 |
| Worker 请求补充 | 主会话先补齐已知信息；必要时展示选项卡 | 卡片回调及原提问者身份核验 |
| 回复含本地报告文件 | 总结带稳定飞书报告链接 | documentDelivery、文件读取和文档权限 |

机器人是否执行业务写入仍由角色、工具权限和本轮授权决定；接话窗口只决定是否响应。撤回来源消息会使相关任务/结果失效，不撤销已被外部系统接受的业务操作。

### 飞书管理指令

群内使用 `@机器人 /subagents list`；私聊可直接发送 `/subagents list`。`/help`、`/commands`、`/status`、`/whoami`、`/agents` 和 `/subagents` 通过宿主指令处理，不为它们同步仓库、整理群历史或创建后台任务卡。`/skill`、`/compact`、普通技能名称及未识别的斜杠请求保留正常任务流程。

命令权限与群聊准入分开：`groupAllowFrom` 是群的准入名单，`ownerAllowFrom` 声明拥有者；仅配置它们不保证命令可执行。宿主按 `commands.allowFrom` 的渠道项/通配项以及飞书发送者 `allowFrom` 判定指令授权。未授权时直接说明原因，不调用模型、不返回“无法生成或发送回复”的通用报错；不会自动修改名单或扩大权限。例如，管理员可在 OpenClaw 根配置设置 `commands.allowFrom.feishu` 为允许发送命令的用户 ID 数组，保存后按宿主配置加载机制应用。

`/subagents list` 查看当前会话的 OpenClaw 子代理运行记录，`/agents` 查看会话绑定的智能体。Agent Repo 右侧面板中的子代理是仓库定义的只读索引；发现定义不等于创建运行记录，也不代替执行器的实际注册和权限配置。

## 开启接话窗口

在全局或目标 `groups.<chatId>` 设置：

```json
{
  "requireMention": true,
  "conversationWindow": { "enabled": true, "durationSeconds": 600, "decisionMode": "auto" },
  "mentionGreeting": "你好，请说明要处理的项目、问题和期望结果。"
}
```

窗口默认关闭，时长支持 30–3600 秒。真人 @ 开启账号＋群＋用户的窗口；窗口内非 @ 文本判断是否继续跟助手聊天。明确 @ 别人时保持安静，附件无可识别文字时仍需 @；窗口不用于 broadcast 多 Agent 群。

`conversationWindow.decisionMode` 可在全局、账号或群配置：

- `auto`（默认）：宿主提供公开 `runtime.decisions.evaluate`，且该群路由的 Agent 有效 `decisionModel` 为 `typesafe/kev-latest` 时，优先使用 Kev；不覆盖 Agent 的显式禁用或其他模型选择，不自行连接服务、下载模型或读取凭证。旧宿主和未配置 Kev 的部署自动使用原来的 `runtime.llm.complete`。
- `off`：仅使用原来的无工具模型分类，不调用 Decision API。

Kev 使用 directed / not_directed / uncertain 三选一，明确标签且对应概率至少 0.8 时采用；该阈值是消费策略，不代表准确率保证。不可用、超时、输入不支持、结果不确定或概率不足时，回退原模型。原模型仍须严格返回 directed 才接话，分类失败则静默；已取消或宿主关闭调用权限时不启动托底请求。Kev 的独立预算为 1500 毫秒，托底模型仍为 8 秒；一次分类可能先后消耗两段预算。

决策只发送当前消息、当前发送者及有界的近期对话/群消息，不发送 Agent 全部系统提示或技能索引。完整 state 与 rubric 序列化后按 UTF-8 **6000 字节**限制，包含 JSON 转义开销，为 Kev-0.8B 的 8K 验证上下文及服务端包装留余量；这不是 tokenizer 的精确 token 计数，也不承诺其他服务配置的容量。先移除最早的整条群消息，再移除较早对话，保留完整当前消息及最近两条对话，并传递省略数量。必要内容仍超限时不发送 Kev，直接走托底；服务端若拒绝输入，同样托底，不截断后重复提交。托底保留原有上下文和当前消息最多 4000 字符的既有处理。

分类调用宿主配置的模型，可能产生额外延迟和费用。接话判定只决定是否受理消息，不提供业务操作或跨会话数据权限。

## 与 Agent Repo / Worker 组合

Main 使用 `feishu_group_history` 按需读取当前群。支持 `start_time`/`end_time`（Unix 秒、左闭右开）及 `page_token`；每页最多50条，保持范围及 limit 不变，用返回的 `next_page_token` 翻页直到 `has_more=false`，按消息ID去重。游标绑定当前账号、群会话及查询范围，宿主重启后需从首页重读。完成分页仅证明机器人可见历史已读完，不保证已撤回消息或附件可用。Main 将必要事实交给 Worker；Worker 本身不注册群历史工具。Agent Repo 模式由 agent-repo 管理角色与项目同步，保持旧 `workspaceSync.enabled=false`，不要同时启用两套同步入口。工作卡、异步完成、结构化提问及报告的协议见后续章节。

报告交付建议先在测试群确认成员能打开文档再用于业务。`documentDelivery` 当前默认启用，但最小接入示例显式关闭，待权限准备后再开启。`[完整报告]` / `[诊断报告]` 标签和链接保持稳定，“上传中”只在占位文档内部显示；上传失败保留总结并报告真实错误，不重新执行业务。

报告权限使用渠道记录的会话类型：群聊授权目标群，私聊授权原提问者的 OpenID，默认均为阅读权限；不把私聊会话 ID 当作群协作者。后台任务会保留该可信类型，后续附件上传复用已确认的同文档、同接收者授权。占位文档写入或授权失败时记录具体阶段及 API 错误码，保留已交付总结。

## 验收与排障

`plugins inspect` loaded、WebSocket ready、收到入站消息、正常模型回复、卡片回执及文档可读是不同验收点。无回复先检查应用已发布、机器人在群、群/发送者规则、@要求及实际绑定 Agent；无历史检查读取权限；文档失败检查本地目录权限、文件存在性、文档 API 和成员访问权限。生产重启、发送测试消息及修改应用权限按管理员授权执行。

Configuration labels and help display Chinese and English together at global, account, group, and DM levels. Keys, enum values, defaults, and validation remain unchanged; no migration or language setting is needed.

Labels and help are shipped through public `uiHints` in both the runtime schema and generated manifest. Load the new plugin version in Gateway and refresh the console. Host controls, validation messages, and the raw JSON editor retain host behavior; user-defined dictionary keys remain unchanged.

## 同事身份与沟通偏好

入站消息复用发送者通讯录查询，附带当前发送者姓名、可见 job_title 和 department_ids（ID 不冒充部门名）；缺失明确为空。缓存按账号、应用和用户隔离，成功缓存十分钟。不会查询全员或推断性格。职位仅用于有标记的受众类型推测，本人设置优先。

本地 `feishu-colleagues/preferences.sqlite` 按 accountId + appId + senderOpenId 保存本人角色及简洁/详细/自动偏好、来源和更新时间，目录 0700、文件 0600。每轮只注入当前用户资料，不更改群会话键或权限。无姓名/职位权限时仍可使用手动偏好。

群内 @机器人后发送独立文本：查看我的画像；设置我的角色：研发（或客服/产品）；设置我的回复偏好：简洁（或详细/自动）；删除我的画像。只匹配完整原消息，不执行引用中的命令；删除只清除本地偏好，不隐藏飞书身份。机器人不建画像。存储异常不阻断业务回复，但明确未保存。自然语言偏好自动提取暂未实现。

画像展示修正：查询用户时明确使用 open_department_id，并逐一查询最多 20 个所属部门的名称；结果沿用十分钟用户缓存。部门查询失败保留错误码，不影响姓名读取。职位区分 available、empty（接口明确返回空值）、unavailable（字段未返回）。个人偏好为空不等于身份画像为空；不自动填写企业职位。

## 按部门配置回复风格

在 `channels.feishu.departmentReplyStyles` 配置有序规则，把当前发送者部门对应的回复风格注入模型输入上下文。例如：

```json
{
  "channels": {
    "feishu": {
      "departmentReplyStyles": [
        {
          "departmentKeywords": ["客服", "客户服务"],
          "style": "先给明确结论和影响，再给客服可执行的处理步骤；附可直接转述给用户的话术。根因未确认或尚未修复时如实说明，不承诺未经确认的恢复时间。"
        },
        {
          "departmentKeywords": ["研发", "软件开发"],
          "style": "给出专业完整的技术分析：结论与确认程度、环境和触发条件、调用链、日志与源码证据、影响范围、修复建议及验证方法。区分已确认事实、假设和未执行项。"
        }
      ]
    }
  }
}
```

规则按配置顺序匹配：任一关键词是当前发送者任一已取得部门名称的子串即命中，不区分大小写，不使用正则；只采用第一条命中的风格，多部门也按规则顺序决定。关键词和风格去除首尾空白。最多 50 条规则，每条 1–20 个关键词，每词最多 100 字符，风格最多 4000 字符。未配置、空列表、未命中或部门名称不可见时不注入风格，保持原有行为。

支持 `channels.feishu.accounts.<accountId>.departmentReplyStyles`：未设置时继承全局，设置后整体替换，`[]` 可单独关闭该账号的匹配。配置表单提供中英字段说明。部门来源复用现有通讯录查询及十分钟成功缓存；关闭 `resolveSenderNames` 后不查询部门，也无法匹配，不从职位、消息正文、引用或部门 ID 猜测。部门变更受缓存刷新时间影响。

命中后，在当前消息前添加独立的“本轮部门回复风格”片段，包含当前发送者、`department_config` 来源与配置的 `style`。不拼入未命中规则，不更改系统提示词或个人画像；画像存储异常也不影响已取得部门的匹配。机器人消息不使用此规则。配置风格作为默认表达指引，优先于职位推测；本轮明确要求、本人明确角色和详略偏好仍优先，证据标准和操作权限不变。只影响当前发送者本轮回复，不能延续到下一位同事。

这里验证的是配置、匹配及实际入站派发上下文，不能保证模型每次生成的措辞完全一致。运行中的 Gateway 需加载新构建和配置后生效；修改本仓库不代表已部署。

## 当前任务修正与回复位置

普通消息继续遵从宿主 `followup` 队列。仅对单 Agent 路由，原发言者在同一会话、同一线程有正在运行的任务时，文本消息以 `更正一下：`、`刚才说错了，`、`改成：`、`补充一下：` 开头并带有具体内容，才尝试 steer。也接受英文冒号和逗号；关键词必须在正文开头，引用、转发或代码块中的示例不触发。其他同事不能用此入口修改当前发言者的任务，原有群准入、权限检查和会话设置仍然有效。

匹配消息有独立的持久入站与串行通道，并跳过文本合批，避免在第一轮结束后才看见修正。宿主确认接纳后，插件等待已开始的发送结束，封存旧卡片已有文字，将后续正文和附件回复到修正消息 ID。切换后暂停此轮的预览更新，结果采用新消息发送，不重写旧卡片。再次修正可继续切到更新的消息；不会修改全局 queue 配置。

没有活动任务、发言者不匹配、广播路由或宿主不接受 steer 时，按普通入站/后续轮处理。持久会话 `/queue` 覆盖配置仍优先，显式设置 `followup` 的会话不会被关键词强制改成 steer。活动回复绑定仅存于内存，重启后不猜测旧任务、不恢复旧卡片写入权。

此功能修正的是 OpenClaw 主会话。已经启动的 `codex_query` 后台进程没有在线 steer 接口，不能声称其参数已修改，也不能盲目重复导出/修复；主会话会收到这项能力限制，核对原任务后说明尚未应用的修正。

回归覆盖句首匹配、引用拒绝、发言者/会话隔离、过期任务、持久入站、实际 bot 交接，以及旧卡片保留和并发附件切换。构建和隔离测试通过不代表真实飞书发送已验证；运行中的 Gateway 需加载新插件构建后才能使用。

## @ 时自动读取群聊历史

真实 @ 机器人且通过群准入检查后，默认使用当前账号读取当前群在这条 @ 消息时间之前（含同毫秒）的最多 20 条可见消息，排除触发消息、已撤回消息、重复消息和晚于触发时间的消息，按时间从旧到新供主 Agent 参考。文本、富文本和卡片沿用插件解析器；不额外下载历史附件或识别图片。不会跨群查询，也不会执行历史中的指令；上下文仍遵守 `contextVisibility` 和发送者准入规则。非 @ 接话的准入机制保持不变。

`channels.feishu.mentionHistory`（也支持账号配置）可覆盖默认值：

```json
{"enabled": true, "limit": 20, "maxChars": 12000}
```

`limit` 范围 1–50，`maxChars` 范围 1000–50000。预算按 JavaScript 字符串长度计算，包含 JSON 转义、身份、时间与说明；这是单轮额外群历史片段的上限，不是模型 token 数或整个长期会话的上限。超限优先从最早的普通历史整条删除，直接引用和话题根消息最后淘汰；若最新单条也超限则不保留该条，历史可为空，不截断 JSON。该轮不再叠加本地 pending/活跃群缓存；原有引用和话题上下文机制独立保留。

请求最多翻 3 页、等待 5 秒；权限不足、接口失败或超时会向模型注明“未取得最近消息”，继续处理当前请求。超时不会继续翻页，但已发出的网络请求可能仍在结束中。不保证一定取得 20 条，受可见性、分页和长度限制影响。

空 @ 默认也进入主会话、带上历史，要求简短接话并询问需求，不自行执行过去的任务。关闭 `mentionHistory.enabled` 时恢复原先的固定 `mentionGreeting` 快捷回复。已有模型会话的压缩策略不受本功能改变。

### 增量历史与紧凑上下文

补拉历史先应用可见性规则，再按可信 `threadId/rootId/parentId` 选择同话题或直接引用，最后执行长度预算与既有模型窗口去重。不按文本关键词猜测话题。有明确关联但候选窗口未命中时，不用其他话题填满；直接引用和原有话题查询仍独立保留，必要时通过群历史工具补查。没有关联 ID 时，只补充最多 5 条近期背景；`limit` 仍是 API 候选数量上限，不保证筛选后条数。

活跃接话窗口使用相同选择器与整条 JSON 预算，并排除触发时间之后的消息。新缓存保存消息类型及话题 ID，空媒体使用类型占位；旧缓存缺少类型时继续按文本兼容，不推测旧记录的媒体或话题。历史补充与当前消息先用结构对象组装，再渲染为兼容旧回执读取的文本，未迁移既有会话记录。

诊断日志 `input history` 只记录协议版本、候选数、相关性淘汰数、预算淘汰数、保留数和字符数；`input assembly` 记录去重前后的总字符数，不记录正文或人员信息。字符数不是 token 数，也不能解释已经存在的长期会话用量。现阶段保留旧历史读取器的标题识别，后续改变序列化格式必须同时维护旧回执兼容。

单 Agent 路由在实际派发前，通过公开 `codex-session-transcript-runtime` 的模型上下文读取接口核对已入库消息。该接口返回宿主当前模型窗口，不把 UI 中可查但已被压缩丢弃的历史视为仍在上下文。比较消息 ID、发送者、消息类型及内容指纹；同 ID 编辑后仍补入。当前请求始终保留，@ 拉取与活跃接话窗口使用同一种历史结构参与去重。

每个 Agent、会话键、会话 ID、账号、群有独立的持久状态，保存在 `OPENCLAW_STATE_DIR/feishu-context/receipts.sqlite` 的 `context_state` 表。只存消息 ID、内容哈希、宿主记录版本和更新时间，不另存正文；目录 0700、文件 0600，清理 30 天未更新的索引。索引仅复用完全相同的宿主快照；新消息入库、编辑、压缩、分支变化或重置后重新核对并替换，不使用永久累积的全群 seen 集合。读取前后检查会话身份和记录版本，发生变化时保守保留补充历史。

只拉取过、排队中、派发失败但未入库的消息不算已读。读取失败或未知旧格式保留历史，不误删；旧版记录缺少消息标识时可能补入一次。取消旧的 8 MiB/10,000 事件整库阈值：在宿主读取快照内逐条处理实际模型上下文，仅保存身份与哈希，历史大附件/工具结果不再直接关闭去重。仍调用飞书 API 获取最新消息，节省的是模型重复输入。广播和 ACP 专用绑定暂不做增量去重。

自动补拉历史直接排除当前机器人自己的应用 ID/OpenID，包括工作卡片、分块及被编辑的回复；在计算消息条数前过滤，不要求发送回执或正文完全匹配。保留其他机器人的消息。这里只过滤额外补拉的历史，不删除模型原生的助手对话记录，也不移除用户明确引用的消息。

入站人员资料合并为一段 `[ConversationPeople]`，同一发送者只出现一次，不再同时发送人员库原始记录和发言者画像。历史段仍位于开头，保持历史去重及摘要协议兼容。普通私聊没有有效姓名、偏好、画像操作、原生提及、身份/账号/邮箱查询或特殊指导时不发送 OpenID-only 人员块；有资料时仅提供必要的身份、可取得的姓名和已设置的偏好，不携带空字段、通讯录元数据或建单指导；群聊按需增加职位、部门、表达角色及本轮原生提及人。查看/保存/删除本人画像的结果始终保留；管理员自定义画像指导仍生效。只在本轮明确提到建单、Issue 或 BUG 时附带简短归属指导，完整资料按需查询。没有新增历史时省略历史段。

采集与模型输入分离：已接纳的人类消息继续将真实发送者和原生提及人存入路由目标 Agent Repo 的 `.runtime/people/people.sqlite`；不同 Agent 不共享此库。`agent_repo` 的 `person`、`people` 和 `people_stats` 查询已存资料，缺失时复用飞书查询补全。异步任务仍固定完整人员快照，不随精简展示或后续资料更正变化。

独立工具 `feishu_user` 查询飞书应用可见范围内的用户，不写人员库、不发送通知，受 `channels.feishu.tools.chat` 控制。参数 `openId`、`email`、`name` 必须且只能提供一个，可选 `accountId`；当前可信账号不能被参数切换。姓名仅查询当前可信群聊的成员，私聊请提供 OpenID 或邮箱；同名返回候选，不擅自选择。权限、可见性、未找到、账号不明确及截断状态由返回值区分，不借用用户登录态。

```json
{"openId":"ou_example"}
```

```json
{"email":"colleague@example.invalid"}
```

这些是 `feishu_user` 的工具参数；若需要人员库中的人工更正或 Gitea 映射，使用 `agent_repo` 的 `{"action":"person","openId":"ou_example"}`，业务写入前仍须核验账号及权限。

回归覆盖重复历史、不同发言者、编辑与恢复旧内容、工具/引用伪造标识、会话重置与过期、压缩及分支边界、读取失败、实际 bot 派发、画像状态和人员映射。构建与隔离回归不等于真实飞书验收，也不能保证模型在所有上下文长度下行为完全一致。

构建与模拟测试不代表飞书权限或线上效果验证；需加载此分支构建后生效。

## Ada 工作中动图与结果提醒

在 `channels.feishu` 或指定账号中配置 `"workingCard": { "enabled": true }` 可启用，默认关闭。插件自带等待/工作 GIF；`waitingImage` 和 `workingImage` 均为可选配置，可分别指定绝对路径覆盖对应素材，未配置的一项仍使用内置 GIF。自定义素材建议保存在插件安装目录外，并确认宿主进程可读取这些文件。对已通过准入检查的单 Agent 真人消息，同一会话已有任务执行时，新请求通过权限和路由检查后立即发送含等待 GIF 的共享卡片；实际开始运行时在同一张卡片换成工作 GIF，最终文本或结构化结果继续原地替换。无需排队时直接显示工作 GIF。没有催问时，等待和工作卡片的正文都只有图片，不含状态说明段落。此模式不显示逐字预览，并关闭文本块流式输出；普通打字状态按原配置保留。仅群聊在结果正文成功交付后，回复结果消息并 @ 原提问者；私聊不额外提醒。

结果卡片已经成功原生 @ 原提问者时，跳过独立完成提醒，包括显示过“干活中”GIF 的群聊任务。结果未提及时，显示过工作 GIF 的任务仍独立提醒一次。后台提交、等待补充信息、失败或取消不发送成功提醒。没有工作 GIF 的旧任务保留近期提及去重：结果或同账号、聊天/线程最近 5 分钟最后 5 条成功消息已经原生 @ 原提问者时，跳过独立提醒；普通文字 @、代码示例和未成功发送的草稿不计。提醒发送失败或结果不确定时不自动重试。

提醒保留原生 @ 的真实用户绑定，自动文案使用不依赖身份推测的“老师”敬称；模型正文按工作区 SOUL.md 选择完整姓名＋同学或完整姓名＋老师（包括领导）。原始姓名、职位和结论引文不改写。提醒使用原生回复关联结果消息，默认文案为“老师，结果已更新，请查看上方回复。”，只表示结果已经交付，不代表业务已成功；`businessMessages.completionMentions` 可设置候选，显式配置 `completionMention` 时使用固定文案，不再重复粘贴结果结论或 Markdown 引文。提醒以同一富文本行中的原生 at 和 text 元素发送，避免 Markdown 段落将称呼换到下一行。提及对象只取入站事件的真实发送者，不取正文里 @ 的其他人。超长结果降级时原卡片仍保留摘录，供定位完整结果。

动图打包在 `assets/ada-waiting.gif` 和 `assets/ada-working.gif`，应用按账号上传并在进程内复用 image_key。使用现有 IM 发卡片、编辑卡片和上传图片接口，不需要 CardKit 流式接口。发送需要机器人、图片上传和消息发送/更新权限。仍需在真实飞书桌面及移动端确认 GIF 自动播放、卡片替换和 @ 通知；构建与 mock 测试不能证明这些客户端行为。

超出单卡预算（28 KB 安全预算）或表格限制的结果走原有分段发送，原卡片更新为摘录；提醒引用成功交付的结果消息。上传或卡片更新失败时继续原有结果发送路径；提醒发送失败只记日志，不重复交付结果或重试不确定的 @。错误、空结果或静默结束会收起动图并给出状态；附件失败保留已交付正文并标注交付未完成。显式更正会封存旧卡片，在更正消息下建立新卡片。存在修改/取消发送内容的 Hook 时禁用此功能以保留宿主的发送决定；广播路由目前不启用。

普通主 Agent 轮次的卡片状态仍保存在当前进程。启用 CodexQuery 异步交付时，可信的 job 受理回执使原卡片继续显示工作 GIF；提交说明不会替换成最终结果，也不会触发“结果已更新”的 @。Ada 结束提交轮次后即可处理下一条消息。

异步 job 与原卡片的关联保存到 `OPENCLAW_STATE_DIR/feishu-async-cards/cards.sqlite`（目录 0700、文件 0600），仅由宿主来源和实际受理的 job 建立，模型正文不能指定卡片归属。后台终态报告仍进入原 Ada 会话 FIFO 核验，随后更新原卡片；只有飞书确认结果更新后、且尚无近期同成员 @ 时才额外提醒原提问者。并行请求各更新自己的卡片；同一轮委派多个 job 时保留已交付结果，未完成部分仍显示工作 GIF。重启后可恢复已持久绑定的卡片；关联写入前崩溃或旧版 job 没有关联时，完成结果沿用普通回复，不猜测卡片归属。关联和已接受结果保留供核对，目前不自动清理。

后台卡片编辑结果不明时，不另发重复结果或提前 @，通知记录进入 uncertain，需核对原卡片；结果已确认而 @ 失败时不重发结果或重试不确定的提醒。超长结果保留原卡片的分段说明，完整结果在下方分段交付，成功后再提醒。源码构建与模拟测试不代表已通过真实飞书验收。

交互提问卡已成功渲染后，Main 本轮产生的提问或等待文字不再单独发送；即使用户在 Main 返回前已提交答案、任务已续跑或提问已取消，也保留原提问卡和当前续跑卡的绑定，避免旧等待回复覆盖新进展。

原提问者也可以用飞书的“回复”直接引用提问卡片，以文字或富文本补充；在群及发送者准入通过后，无需再次 @ 机器人。渠道按真实账号、聊天、发送者和被回复卡片匹配当前问题，与表单共用一次性答案保存和原 job/question 的续跑入口。原卡片显示文字补充及受理状态，后续工作卡继续展示原任务进度。文字原文交给 Main 按原问题理解，不猜填必填日期或选项；仍需澄清时在原卡片显示提示并恢复填写入口。长文字仅在卡片中展示摘录，保存和交接完整原文；撤回文字补充会使其来源失效；已接纳该补充的后台任务会收到取消请求。其他成员、其他聊天或已失效的问题不能通过回复接管原任务；同一回复重放、文字和表单并发只提交一次。

Worker 上下文请求在 Main 真正开始执行时才标记可能已处理；Gateway 排空期间拒绝受理、尚未启动 Main 且没有可见发送时，原通知保留 pending 重试，沿用原 job 和 questionId。宿主暂忙时拒绝转存到宿主 followup 队列，由原通知保留 pending 重试；未确认 Main 启动不记录工具协作回执。Main 已启动或消息发送开始后发生错误、停止或正常返回但缺少回执，仍进入 uncertain，不能自动重放。已确认 delivered/suppressed 的终态不被迟到回调覆盖；旧服务的启动回调始终使用原停止信号。旧版留下的 uncertain 必须先核对原会话执行、reply 事件及飞书消息/卡片回执，确认未处理、未发送后才由管理员恢复原通知；不得重建业务任务或重发已确认的结果。

启用步骤：构建打包，按仓库安装流程加载新版本，再配置 `workingCard.enabled`。代码提交不会修改运行中 Gateway 的配置或自动重启服务。

### 等待卡片的队列边界

启用工作卡片的真人单 Agent 请求，在渠道准入后按账号与 Agent 会话串行执行，每条请求保留自己的卡片、提问者和回复位置。持久入站的延后认领释放接收通道但保留消息与心跳；传输队列在完成准入交接后继续处理后续消息，避免整段模型执行阻塞等待提示。未通过准入的消息不发图。此功能开启时，独立请求先在插件 FIFO 等待，再进入宿主；宿主的 collect/interrupt 等设置不能绕过这层等待。即时更正、旁问和控制命令不走这层 FIFO。

已确认属于当前执行任务的同一发送者更正沿用既有 steer 流程，不另建等待卡片。已授权停止指令同时取消该发送者在当前会话尚未开始的请求，更新其卡片；其他人的排队请求保留。异常、取消和无结果时仍使用必要文字收起动图。未知发送结果不重发卡片；等待图更新失败仍尝试交付最终结果。

等待卡片身份和执行 FIFO 保存在内存，未开始的消息仍由持久入站保管；进程重启可重放未认领消息，但不能接管重启前已经发出的卡片，可能遗留旧等待图。此限制与工作中卡片的崩溃恢复边界相同。

### 催问当前任务

同一真实提问者、账号、会话和线程内，明确短句如“好了吗”“还要多久”“上面的任务怎么样了”会绕过普通任务队列和文本合批。通过渠道准入后，只查询当前运行的工作卡片，不再发起模型或业务任务。其他发送者、引用不相关消息、复杂新请求、无活动任务或重启前任务不会接管卡片，按普通入站处理。广播和未启用工作卡片的场景不适用。

新卡片上方工作 GIF，下方简短安抚、已完成/正在做/待做、估时或未知说明。先确认新卡片发送成功，再调用 IM 撤回接口撤回当前轮旧占位卡；最终结果和原生 @ 结论提醒使用最新卡片。正文与附件发送同迁移串行，已经交付的结果卡不撤回。创建失败或状态不明时保留原卡且不重试；撤回失败时尝试把旧卡标记为“进度已移到下方”，新卡继续承接结果，不把失败说成已撤回。

`ada_task_progress` 工具只记录当前运行的公开阶段快照，按可信会话、账号、真实发送者绑定，不允许参数指定目标。使用工具白名单时需加入此工具。主 Agent 应在真实阶段变化后更新 completed/current/remaining；estimate 可选，必须含剩余分钟范围和依据，过时后明确提示估时已超过。没有记录时仅基于宿主公开计划/工具启动事件说明已知状态，不编造完成量、后台子步骤或 ETA，不展示工具参数和内部推理。重启会丢失快照；记录成功不等于发送或任务完成。

需要机器人撤回自己消息的相应权限；实际飞书客户端中的撤回、GIF 和引用效果仍需真实会话验收，mock 测试不代表外部发送成功。

正文点名使用 `<at id="真实 open_id"></at>同学` 或 `老师`，卡片直接使用原生提及，富文本消息转换为原生 at 元素并保留后缀和位置。当前发送者与本条消息提及人员提供姓名/ID 映射；不根据姓名猜 ID。代码、引用中的示例和 @all 不通过此转换激活。

## 旧版对话前固定同步（兼容入口）

新架构由独立 `agent-repo` 插件通过 OpenClaw 原生钩子完成调度前仓库同步；飞书插件只负责消息准入、任务旁路与正常回复。以下 `workspaceSync` 暂留兼容，不自动切换或关闭。`agent-repo` 的 `--prepare-sync` / `--prepare-migration` 计划会停用全局旧同步并保留其其他字段用于回退；账号级覆盖需要管理员单独处理。旧 Feishu 同步与 Agent Repo 原生同步不得同时启用；新插件会拒绝双开配置以免重复更新和上下文冲突。计划与本地测试不代表生产已切换。详见 [Agent Repo 原生同步说明](../agent-repo/README.md#独立的原生同步入口)。

使用旧兼容入口时，在实际 `channels.feishu.workspaceSync`（或账号配置）设置 `{"enabled":true,"root":"/absolute/path/assistant-workspace","timeoutMs":30000}`，默认关闭。插件在真人普通消息通过渠道准入后、交给任何模型前，固定等待同步完成，不向模型提供同步工具，也不靠提示词调用。每个入站对话轮次分别执行，无 TTL 或“最近拉过就跳过”；同一工作目录并发同步串行。重放去重、合批仍沿用宿主流程。已匹配当前任务的催问、停止以及 `/stop`、`/abort`、`/status` 不启动新的资料轮次，保持可及时操作；斜杠技能请求仍先同步。

主仓库每轮抓取 `origin/main`（部署方仓库）和 `upstream/main`（公共上游），按这个顺序整合；`wiki` 仍只快进到它自己的 `origin/main`。设置 `includeUpstream:false` 可恢复旧的仅 origin 快进模式；默认开启双来源，缺少 upstream 时报告失败，不静默跳过。根目录必须 main；wiki 允许 main 或无本地提交的 detached HEAD。管理员首次须准备好远端、Git 提交身份及已初始化的 wiki 子模块。

双来源先用 `git merge-tree --write-tree` 预检，再以 `git commit-tree` 生成必要的本地合并提交，最后一次性快进应用预检结果。冲突或不相关历史不修改 HEAD、索引和工作树；不调用模型解决冲突。`.git` 对应的工作树 Git 目录中 `ada-workspace-integration.json` 记录本流程最后整合的精确 HEAD 和远端来源，以便下轮继续整合；用户自己的额外提交、来源变化或缺失的记录不能冒充自动合并。生成的合并提交不自动 push，分享更新仍走人工维护流程。需要支持 `merge-tree --write-tree` 的 Git；记录丢失或更新后进程崩溃导致记录未写入时，保留现场由管理员核对。

根仓库未暂存的子模块偏移不阻塞同步；根文件改动、已暂存项（含 gitlink）、用户本地未推送提交、知识库脏文件、未结束 Git 操作或同步超时会保留现场并阻止本轮进入模型。网络/认证原始 stderr 不发到群里。不 stash、reset、切分支或更新其他业务子仓库，不暂存 wiki gitlink。根成功而 wiki 失败时可能部分更新，下轮重新完整核对；角色/技能刷新不因前次失败而跳过。同步进程默认设置 `OPENCLAW_WORKSPACE_SYNC_ACTIVE=1`，供项目 post-merge Hook 按需跳过其他维护；不修改永久 Hook 配置。已有 Hook 若依赖其他环境标记，须在私有 `workspaceSync.gitEnvironment` 中显式保留相应配置。

同步成功后核对本轮各 Agent 的实际 workspace 与同步根目录一致，再建立 Git 中 `skills/`、`.agents/skills/` 的普通 `SKILL.md` 文件索引。技能树（含正文、references、assets）或 `AGENTS.md`、`SOUL.md`、`IDENTITY.md`、`USER.md`、`TOOLS.md` 的版本变化会改变刷新标识。公开 `before_prompt_build` 钩子在模型执行前将精简索引放入系统上下文，要求先审阅当前列表、读取任务相关技能；无需依赖原生文件监听的延迟。同步后的技能与角色指纹还会原子发布到本机 `codex-query-sessions/skill-versions`，供后台执行会话在下次 run 时判断是否需要刷新。发布失败阻止本轮进入模型，旧执行会话和正在运行的 job 不被批量修改。它不替换 OpenClaw 内部技能缓存、不授予被禁用技能或额外工具权限，也不把所有技能全文塞进输入。索引每轮保持稳定，避免会话重置、压缩或临时系统上下文未入历史后丢失；版本未变无需重复读取技能。索引超过 500 项或 60,000 字符时阻止新轮并报告，不静默截断。

已安装 OpenClaw 2026.9.5 的原生 bootstrap 每轮重读角色文件、比较内容并更新缓存；因此新轮使用同步后的角色预设，不另行复制一份角色正文，也不修改模型、工具权限或 Gateway 配置。已运行的模型不会中途被改写。需要宿主启用插件的提示词钩子并采用原生 bootstrap；外部 ACP Agent 的技能/角色热加载不在此保证范围。该功能是管理员授权的宿主维护流程，不扩大 Ada 或 codex_query 的 Git 权限。日志记录 origin/upstream 整合后的根提交、upstream 和 wiki SHA；生产插件部署及真实会话验证单独进行。

## 任务来源与消息撤回

单 Agent 真人任务自动绑定稳定 taskId、版本和来源消息 ID，包括本轮实际合批的请求、实际读取的直接引用，以及宿主已经接纳的同一提问者补充。群聊历史只作为参考，不把最近 20 条消息都当作任务授权。普通等待/工作卡片仍只有 GIF，内部任务标识不强制显示在卡片上。

收到官方 `im.message.recalled_v1` 后，插件按可信账号、聊天和来源消息 ID 匹配；本人、群主和管理员撤回均按来源失效处理。撤回事件使用独立持久入站通道，不等待前面的任务结束。全部请求来源撤回（即使仍有引用）时取消排队或中断主会话，停止旧结果与完成 @；部分撤回且仍有请求时中断旧版本、等待主会话返回，再用剩余消息建立新版本。引用保留用于撤回追踪，但不能独立保持任务可执行；仅有引用的来源集合不激活执行租约。收到撤回前已在途的发送不能保证撤销；已交付结果不会自动删除。普通停止指令与其他人的任务仍隔离。

`codex_query` 从宿主执行上下文绑定来源，模型不能指定其他人的任务。来源写入后台 job，撤回会为匹配的未结束 job 持久写入取消标记；worker 最多约一秒检查一次并终止本地 Codex 子进程组，启动前也检查。失联 worker 同样保留取消标记，不能把“已请求取消”称为已停。取消不回滚外部已接受的操作；调整时先 status/wait 核对原 job 和业务记录，未确认结束或状态 unknown 时不得重新执行。

来源索引与撤回记录保存在 `OPENCLAW_STATE_DIR/feishu-source-tasks/tasks.sqlite`，目录 0700、文件 0600，仅含身份/消息 ID、状态和版本，不持久保存消息正文。目前保留记录供审计，暂无自动清理。撤回先于任务准入也会生效；后台 job 可跨 Gateway 重启取消，但重启不会自动重建旧主会话、恢复卡片或自动续跑部分撤回后的剩余任务。历史版本创建且没有 provenance 的 job 不猜测归属。ACP 专用绑定和广播不是本功能支持的 Ada 单 Agent 路径。

部署还须在飞书应用的“事件与回调”中订阅应用身份“消息撤回”，发布变更；已有 `im:message` 或 `im:message:readonly` 任一权限即可，参见[官方事件说明](https://open.feishu.cn/document/server-docs/im-v1/message/events/recalled)。事件监听、构建测试与健康检查不代替真实会话端到端验收。

工作卡片仅在回复交付队列结束后收尾。宿主停止输入提示（包括 typing TTL 到期）不会封存结果卡片，也不会提前解除撤回监听、催问或更正绑定；任务实际结束后才清理这些绑定。

## 上下文与并发回归边界

历史去重、任务修正与部分撤回重建后同步宿主规范字段 agentText/rawText/commandText；撤回当前附件来源时同时清空规范 media。接话窗口补充记录进入 agentText，仍作为不可信参考。普通斜杠技能请求参与工作队列，只有停止、状态和旁路消息等明确控制入口绕过；等待期间不覆盖正在执行任务的来源租约。回归使用真实公开 SDK finalizer，并检查实际模型正文。

## 上下文片段标识

插件生成的消息上下文统一使用 `[类型: 中文名称]`，标题与内容分行：

- `Context`：发言者资料、相关人员、引用、群历史和工作区技能索引。
- `Guidance`：资料使用规则、部门回复风格、@ 语法和工具使用说明。
- `Metadata`：消息 ID、内容指纹、任务来源和工作区版本。
- `Notice`：读取失败、权限不足、任务修正和撤回状态。
- `Request`：当前消息，或撤回后剩余的有效消息。

类型表示片段用途，不改变消息实际角色，也不授予操作权限。普通正文不再用 `System:` 冒充系统消息。画像数据与固定表达指导分开，引用独立于当前请求。部门风格仍在本轮消息正文内；工作区索引仍通过宿主系统上下文钩子注入。群级自定义 systemPrompt 保持原文。

新历史标题为 `[GroupChatHistory]`，下一行是包含 messages、读取状态和摘要的 JSON 对象，不附加固定解释。默认所有块采用数据类型名；冒号仅用于必要的语义消歧。字符预算包含标题和数据。去重读取器同时兼容旧历史、当前消息和飞书消息标识，不迁移或重写已有会话。标题统一不会改变历史筛选、权限检查或宿主压缩策略。

## @ 与引用消息的历史窗口

群聊明确 @ 或回复消息触发时，默认读取最近 20 条候选（`mentionHistory.limit`，实际至少为 `recentLimit`，默认 5），每轮保留最近 5 条可见历史消息，包括机器人的回复。最近 5 条不因话题筛选、已在当前模型会话中出现或压缩次数而省略（超长时逐条用明确标记的摘要或摘录表示）；当前触发消息单独保留，不计入这 5 条。接口重复返回同一条记录时仍只保留一份。

回复引用消息时，按原消息时间额外查询同群前后各 3 条可见消息，只读取触发时间以前的记录。引用邻近记录与最近窗口重叠时由最近窗口承载；更早记录沿用当前模型可见上下文的 ID 与内容指纹去重，压缩或重置后重新判断。权限过滤始终生效；没有权限的消息不会为了凑数注入。邻近消息时间与原消息完全相同、无法判断前后顺序时不纳入前后窗口。

`mentionHistory.maxChars` 是默认摘要触发预算；最终组装时先跨轮去重，再对超限内容生成摘要。必带窗口每条保留，但不保证超长消息完整原文全部注入。来源元数据和当前请求不计入摘要正文目标，最终长度仍可能高于目标。飞书接口失败、超时、记录不足或有界分页不能取得完整窗口时不伪造消息，并输出提示；引用邻近查询超时仍保留已取得的最近窗口。关闭 `mentionHistory.enabled` 则关闭这条拉取路径。

### 历史策略配置页

插件 UI 的“@ 与引用历史”分组可配置下列字段；全局和账号级均可用。账号仅覆盖填写的字段，未填写字段继承全局。没有配置时沿用上述行为。

| 字段 | 默认值 | 范围与含义 |
| --- | --- | --- |
| `enabled` | `true` | 启用 @ 与引用历史读取 |
| `recentLimit` | `5` | 1–50，每轮必带原文或明确标记的摘要，不做跨轮去重 |
| `limit` | `20` | 1–50，候选数量；实际至少为 `recentLimit` |
| `quoteBefore` | `3` | 0–20，引用原文之前的条数；0 关闭 |
| `quoteAfter` | `3` | 0–20，引用原文之后的条数；0 关闭 |
| `deduplicateOlder` | `true` | 对必带窗口之外的消息进行跨轮去重 |
| `maxChars` | `12000` | 1000–50000，默认摘要触发预算 |

路径为 `channels.feishu.mentionHistory` 或 `channels.feishu.accounts.<accountId>.mentionHistory`。关闭更早消息去重不会取消权限、关联筛选或长度限制。配置表单由插件 schema 与 UI hints 生成，Gateway 需加载新版插件才能显示新增字段。

### 连续引用链

回复消息时，插件沿飞书 `parent_id` 逐级读取完整引用链，不将同话题的其他消息猜测为父消息。直接引用原文只承载一次，祖先与群历史合并到统一历史区按从早到晚排列，保留 ID 和回复关系；每轮重新读取，不依赖压缩前的上下文。各层逐一检查可见权限，不跨群追溯；断链、撤回、无权限、循环、超时或读取预算不足时保留已取得内容并明确提示不完整。每条引用都登记为独立任务参考来源，撤回时可以按原始消息 ID 处理。

开启 `conversationWindow.enabled` 后，需要 @ 的单 Agent 群聊也接受回复链激活：当前消息无需重复 @，只要已读取、同群且可见的任一父消息包含当前机器人的原生 @，即可开启或续期当前回复者的接话窗口。窗口仍按账号、群、当前发送者隔离，时长沿用 `conversationWindow.durationSeconds`（默认 600 秒），不继承原消息作者的授权。普通文字“@Ada”、其他机器人、跨群或不可见引用不触发；当前消息明确 @ 其他人时保持静默。发送者准入检查先于读取，引用链的深度、预算和 5 秒超时继续生效；准入时读取的内容在本轮上下文中复用，不再重复读取，也不为这次激活额外调用分类模型。

机器人原生提及兼容事件中的 OpenID 和消息查询接口返回的 `id_type=app_id`；后者必须精确匹配当前飞书账号的 AppID，不按显示名称识别。诊断日志 `reply chain activation` 仅记录已读取层数、不完整标志、匹配和准入结果，不输出原文及身份标识。

插件 UI 的“连续引用消息”可配置 `quoteChain.maxDepth`（默认 20，1–100，包含直接引用）和 `quoteChain.maxChars`（默认 24000，1000–100000，参与默认摘要触发阈值）。账号逐字段继承全局配置。设层数为 1 恢复仅读直接引用。该功能独立于 `mentionHistory.enabled`；引用前后窗口仍仅围绕直接被回复消息读取，不为每层祖先再扩展邻近消息。读取超时上限为 5 秒。

### 超限历史 AI 摘要

群历史、引用原文、引用链和首次话题历史按消息 ID 合并，同一轮同一条只承载一次；最近必带标记保留。权限筛选后，先按模型当前可见原文对更早历史去重，再计算统一字符预算。最近 5 条原文能放下时优先保留；超长时每条仍有摘要或摘录记录。当前请求保持原文，历史不能提供新的操作授权。

超过阈值时，通过宿主 `llm.complete` 调用当前 Agent 的模型（可覆盖），不调用 codex_query、不执行工具、不写长期记忆。每条摘要的消息 ID、父消息、来源标记、内容指纹由插件填入，并校验模型返回覆盖全部待总结消息。摘要明确标注 `历史消息摘要（AI 生成，非原文）`，不代表事实已核实。摘要不写入“已读原文”索引，因此压缩或后续需要细节时仍可重新取原文。

调用超时、模型不可用、输出不合规、超过读取预算或关闭 AI 时，降级成逐条首尾摘录并标注 `原文摘录，非 AI 摘要`，不声称摘要成功。摘要正文有长度目标，来源元数据和当前请求另计；这不是整个模型输入的硬 token 上限。当前实现不跨请求缓存摘要，避免编辑、撤回和权限变化沿用旧摘要；超限请求会增加一次模型调用的延迟与用量。

全局 `channels.feishu.historySummary` 及账号同名配置支持 UI 设置：

| 字段 | 默认 | 含义 |
| --- | --- | --- |
| `enabled` | true | 启用 AI 摘要，关闭时使用明确标记的摘录 |
| `triggerChars` | 12000 | 未设时取群历史预算与引用展示预算中的较小值 |
| `targetChars` | 4000 | 摘要正文目标，按触发阈值的一半分配；消息很多时为保留逐条信息可能超出，来源元数据另计 |
| `timeoutMs` | 8000 | 超时返回摘录，并取消摘要请求 |
| `maxInputChars` | 200000 | 原文读取预算，与展示预算分开；过长原文不发送给摘要模型 |
| `model` | 当前 Agent 模型 | 可填 provider/model；沿用宿主的模型和凭证路由 |

引用链只因深度、读取预算、权限或超时停止，不再因展示阈值停止；分页后续失败时保留此前已读取的最近窗口。摘要缓存不持久化，任务来源和撤回处理始终绑定原始消息 ID。

## CodexQuery 异步结果入队

与启用 asyncCompletion 的 codex-query 配合，后台完成事件进入现有群工作轮次 FIFO，等待当前轮次结束后再启动 Ada 结果核验。事件直接携带报告内容与路径，Ada 无需再次查 job 或读取普通报告。使用 followup，原始请求和后台执行不重跑。

通知第一行使用 `[CodexQueryResult: 异步任务结果-处理规则……]` 包含标题与完整处理规则；完整 JSON 紧跟下一行，作为参考数据，不增加结果起止标记。给 Ada 的通知保留完整 `codex_query.completed` 事件结构：`type`、`eventId`、`jobId`、`topic`、`status`、`provenance`、`reportContent`、`reportPaths`、`reports`、`experienceReview` 与实际时间字段。新增 `request` 携带经过宿主绑定校验的原始提交目标 `task`、必要上下文 `context`、执行约束 `constraints`，以及 `availability`。它是 Ada 提交给执行器的任务上下文，不代表完整群聊历史；不混入完成时当前群的其他请求，也不传输执行器凭证或整份 memory 参数。原始上下文或报告缺失时显式标记，旧事件没有 request 时标记 `legacy_event`，不能把可能截断的 `taskSummary` 当成完整任务。

Ada 直接对照原提交与报告中的结论、证据、未完成事项交付，不例行调用 list/status/wait、群历史或再次读取已附正文的报告。`reportContent` 保留完整执行结果，`reports[].content` 保留详细报告原文，路径、缺失原因、业务字段和下载链接均保留。只有必要信息明确缺失时才补查；执行器终态和时间不代表业务已核验成功。通知块明确上下文和报告均为参考材料，不重新执行、不从报告取得新授权；经验候选仍需按现有规则复核。来源核验、撤回、FIFO 及原卡片更新流程不变。

投递前、出队时及发送前核对原任务来源、版本和撤回状态；报告只是参考数据，不提供新授权。存在已验证的异步卡片关联时，先更新原卡片，再回复该结果消息并原生 @ 原提问者；旧版 job 或未启用工作卡片时回复原群和原请求消息。后台进程不负责飞书发送，发送回执由适配器返回并持久化。未得到回执的在途发送需人工核查，不自动重复发。不同群独立排队；Gateway 重启后的恢复由 codex-query 的持久任务记录负责。

完成适配器在注册时绑定本插件的公开 runtime。跨插件回调不依赖调用方的 runtime 槽位，兼容宿主对插件实例的隔离；处理结果与发送前都读取最新会话记录，已更换的主会话不接收旧结果。

原工作卡的结果更新回执确认后，成功、失败、超时和取消终态均可原生 @ 原提问者。成功保留 `businessMessages.completionMention` / `completionMentions`；失败、超时、取消分别使用 `failureMention`、`timeoutMention`、`cancelledMention`，支持全局和账号级配置，不使用“搞定了”等成功文案。来源撤回、会话失效或卡片更新结果不确定时不提醒；已有提及的去重和工作 GIF 的单次提醒规则保持不变。上传完成不另发第二条提醒。

`businessMessages` 同时控制同步与异步卡片文案；`asyncOversizedResult` 保留异步长结果提示的原默认值。进度模板的占位值也可配置：`progressInitial`、`progressNext`、`progressRun/Wait/Status/List/Cancel`、`progressBackground/Tool`、`progressSeparator`、`progressEstimate/EstimateExpired/EstimateUnknown`、`progressAge`、`progressNoCompleted`、`progressDeliver/Await`。其中估时模板支持 `{minMinutes}`、`{maxMinutes}`、`{basis}`，时间提示支持 `{minutes}`。`conclusionKeywords` 和 `emptyConclusion` 对结果卡片摘要及结果摘录同时生效。

## 本地报告的两阶段飞书交付

Worker 完成报告的飞书文档默认以“Worker 会话名称（topic） YYYY-MM-DD”命名，例如“订单导出排查 2026-10-29”；日期取任务完成时间，固定使用 Asia/Shanghai 时区。占位文档与直接上传使用相同规则，本地报告路径和文件名不变。缺少会话名时使用原任务摘要，再缺失时使用“Worker报告”；旧事件缺少完成时间时使用本次交付日期。普通文件交付仍取文件名。未配置标题模板或使用默认 `{filename}` 时启用此规则；其他自定义 `titleTemplate` 保持优先，Worker 模板可使用 `{filename}`、`{sessionName}`、`{date}`。只影响新建文档，不批量重命名历史文档。

普通真人任务和 CodexQuery 完成结果包含本地报告时，采用两阶段交付：先创建并授权一份内容为“上传中”的飞书占位文档，将总结更新到原工作卡片；所有本地报告入口保留原来的文案，例如 `[完整报告](占位文档 URL)`、`[诊断报告](占位文档 URL)`；聊天入口不显示“上传中”，点击文档后才看到固定的上传说明。第一阶段确认卡片回执后结束 Ada 本轮，后台再读取完整报告、写入同一文档并上传附件，完成后替换占位文档的正文，并按需要刷新原卡片；文档地址与报告入口标签保持不变。原有业务 HTTP 下载链接保持不变。 占位文档已确认的目标权限在后台复用；文档、目标或权限变化时才重新授权。上传成功且可见正文未变时只填充文档并结束后台工作，不进入 Main FIFO 或重复 PATCH 卡片；失败提示、附件转换说明等可见变化仍更新原卡片，保留其他任务的最新结果。

上传队列存储在宿主状态目录 `feishu-document-uploads/uploads.sqlite`，不依赖主会话持续等待，最多同时处理两个上传任务。后台编辑再次进入该会话 FIFO，只占用实际卡片更新时间；多个 job 共用卡片时，重新合并已交付的其他结果，避免旧上传覆盖新结果。不再发送第二条完成提醒。每次写入重新检查来源版本、撤回状态及会话 ID；撤回或会话重置后不交付旧报告。

上传失败或重启中断会保留已交付总结，文档正文显示“上传未完成”，聊天保留原报告入口并附上传失败说明。尚未开始的队列可在重启后继续；已经开始但结果不确定的上传不自动重复，改为说明中断。卡片编辑失败时仅对同一消息最多重试三次，不重新上传文件、不新发消息；仍失败记录为 `update_failed`；文档可能已经可读，需管理员核对。后台队列不保存认证配置。第一阶段仍需少量创建、写入和权限 API，请勿将“先交付总结”理解为零接口耗时；日志分别记录占位文档、后台准备和最终卡片编辑的耗时。

仅处理明确的本地文件链接及本地附件参数。交付前使用共享方法检查路径是否为存在的文件；不存在或是目录则跳过，不发起读取和上传。存在但读取或上传失败仍保留真实错误。Markdown 转文档正文失败时，继续将原始 MD 上传为文档内附件。

附件大小超过 1GB（1024MB，1073741824 字节）时，在读取文件正文前跳过，不加载到内存、不上传，也不占用附件数量和总大小预算；报告内引用的附件同样处理。文档和最终聊天总结末尾追加“附件未上传说明”，列出文件名、实际大小和超过 1GB 的原因。其余报告和附件照常处理；全部附件均超限时仍将说明写入文档（包括已有占位文档），不会一直显示“上传中”。等于 1GB 不触发此跳过规则，现有单文件/总大小读取限制仍有效，并不扩大上传额度。

未启用文档转换、没有本地文件、来源绑定不足、带必需机器人提及或超大结果走原有发送/分片路径。直接发送与手动卡片编辑保留同步转换协议。

`channels.feishu.documentDelivery` 默认启用，也支持账号级覆盖。回复包含本地文件引用或本地附件时，插件将文件整理为一份飞书文档：正文及 `.md`、`.markdown`、`.txt` 文件内容进入文档正文，`.sql` 默认以保留原文的 SQL 代码块进入正文，原文件、图片及其他附件作为真正的文件附件块加入该文档，聊天保留原回复总结，只将已上传的本地文件引用替换成飞书文档链接；仅通过 media 参数传入附件、正文没有对应引用时，在原总结后追加文档链接。Markdown 报告内部引用的相对图片和证据文件也加入同一文档。没有本地文件的消息保持正常发送；HTTP 链接和代码围栏中的示例路径不触发扫描，不遍历目录。

正文支持 Markdown 本地文件链接及图片链接，目标可为绝对路径、相对路径或 `file://`。普通文本和代码里的路径、`MEDIA:` 文本及 HTTP 链接不触发文档附件上传；显式本地 media 参数复用相同路径解析。相对路径以 `documentDelivery.workspaceDir` 为准；未设置时使用工作区同步目录或 Agent 默认工作目录，无法确认工作目录时拒绝相对文件交付。文件读取使用宿主 media 权限与沙箱规则；`localRoots` 只声明允许读取的目录，不绕过已有工具文件权限。

消息中的图片（包括本地 PNG、GIF 表情和 Markdown 图片引用）直接走聊天媒体发送，不上传飞书文档。图片与报告同时出现时，报告生成文档，图片仍在聊天交付；报告文件正文内部引用的图片继续作为报告附件。

普通 Agent 回复和 CodexQuery 完成交付未显式配置读取目录时，使用宿主公开 SDK 为当前 Agent 计算的 media 目录与其工作区。显式 `localRoots` 或交付权限仍优先；不按报告引用自动放开其他目录。异步交付使用飞书插件注册时绑定的 runtime，避免跨插件调用时取错 runtime。文件读取、文档准备或附件上传失败时，仍交付 Ada 的原始答复，并注明附件未成功交付；本地报告、源码和角色文件的全文只用于生成文档，不因失败自动展开到聊天正文。实际消息发送失败仍保留交付错误，不标记为已交付，也不发送完成提醒。

报告正文的 `/1.681776MB` 等数值、体积或比例不作为裸文件路径；真实同名文件可通过明确的 Markdown 链接交付。Ada 的最终回复在准备文档前写入状态目录的 `feishu-completion-outbox/outbox.sqlite`。未开始发送时的重试直接使用该回复，不再次提交相同的完成事件给模型；仍经过所属主会话 FIFO，并重新检查任务来源、版本、事件内容和 session。收到飞书回执后删除待交付回复；发送结果不确定时继续保留原隔离规则，不自动重复发送。

本地链接及报告内引用的文件已不存在时跳过该文件，继续整理正文和上传其余有效文件。全部引用文件均不存在时不创建空文档，直接交付正文，失效本地链接转为普通文件名称；权限拒绝、文件超限和文档接口失败降级为文字结果，不发送失效本地链接或未完成文档链接；不因附件失败重新执行后台业务。

```json
{
  "channels": {
    "feishu": {
      "documentDelivery": {
        "enabled": true,
        "workspaceDir": "/srv/assistant-workspace",
        "localRoots": ["/srv/assistant-workspace", "/srv/assistant-artifacts"],
        "maxFiles": 20,
        "maxFileMb": 20,
        "maxTotalMb": 50,
        "maxTextChars": 200000,
        "textExtensions": [".md", ".markdown", ".txt", ".sql"],
        "titleTemplate": "{filename}",
        "linkTemplate": "已整理为飞书文档：[{title}]({url})",
        "grantToTarget": true,
        "permission": "view"
      }
    }
  }
}
```

`folderToken` 可指定机器人可写的云空间文件夹；未配置时使用机器人默认云空间。`urlBase` 可覆盖文档链接域名；默认使用飞书域名，Lark 账号使用 Lark 域名。标题支持 `{filename}`，没有可替换的本地引用时，追加链接的文案使用 `linkTemplate`，支持 `{title}` 与 `{url}`，其中 `{url}` 必须保留；已有 Markdown 本地文件链接则保留其标签并替换目标 URL。单文件上传受飞书素材接口 20 MB 上限约束。

文档默认只向消息的目标聊天或用户授予查看权限，不设置公开分享。机器人需要文档创建/写入、素材上传及协作者授权能力；关闭 `grantToTarget` 仅适合目标文件夹已有正确权限的环境。Markdown 正文转换或写入失败（含正文超过配置上限）时，在同一份文档追加提示并交付原始 `.md` / `.markdown` 文件及其他附件，保留文档链接；不清空可能已写入的部分正文。读取、附件绑定、降级提示写入或授权失败时，改用文字交付，并注明附件未成功交付；不将本地路径或未完成文档当作下载链接。可能留下未完成文档，不自动删除。取消、撤回和发送权限失效仍停止交付；只有正文实际发送或原卡片实际更新成功才发完成提醒。

普通回复、异步任务结果、直接发送、原生卡片及卡片编辑复用文件转换逻辑；已绑定任务的普通最终回复和异步完成结果采用上述两阶段流程。为避免预览分片提前显示本地路径，启用此功能时正文等待完整回复后发送，等待卡片与进度仍可使用；关闭后恢复原来的流式预览和附件直发行为。语音、远程媒体若随本地文件一起交付，也作为文档附件处理。文档评论目标沿用原评论逻辑。

本地 mock 测试验证了请求顺序和失败边界，真实租户的附件块 API、应用权限、成员可见性和聊天交付需要部署后验证。

## 后台完成报告

给 Main 的模型输入保留一个正文来源；与 `reportContent` 相同的正文用 `contentRef`/`resultContentRef` 引用，重复任务上下文用 `requestRef` 引用。宿主汇总文件不再重复展开已有结果和审计字段；持久化完成事件、报告文件和不同报告正文仍保持完整。Main 直接对照引用字段，无需为相同正文再次读文件。

CodexQuery 异步结果沿所属 main 会话 FIFO 处理。Worker 执行和完整原始报告保持客观，不应用提问者的身份或回复风格；表达适配由 Main 交付轮次承担，不为风格重做任务或覆盖原始报告。完成事件保留原任务、完整报告与路径；main 对照原任务核验，按原提问者的本人角色和详略偏好总结，继而采用部门配置和职位推测的表达指引。研发侧重证据、改动及验证，客服侧重操作和话术，产品侧重规则与决策；未知角色先简明结论。画像不可用仍交付，不借用最近其他发言者的角色；读取画像不执行任何偏好设置命令。

后台完成回复允许只有图片附件、没有文字，插件仍保存待发载荷并发送原生图片，收到发送结果后才记录交付回执；附件失败时复用待发回复，不重复调用 Main。普通完成事件和协作请求均由插件保留重试控制，宿主忙碌时不把交付回调留在宿主延后队列中。已经生成结果但未获回执的历史任务须核对原记录后恢复，不能靠重新生图修复投递。

main 最终总结末尾须附完整报告的 Markdown 链接 `[完整报告](<完整绝对路径>)`，不放进代码围栏或仅列文件名。宿主在模型漏附链接时，优先补充已确认的主报告（有效 Worker 原报告优先，缺失时使用宿主兜底），其次使用本事件中已捕获正文的报告；不为未落盘、未绑定或读取失败的报告编造链接。链接随待交付回复持久化，重试不重复调用模型。飞书插件转换该引用并保留总结，聊天给适合该用户的结果摘要，详细报告单独保留；必要业务字段、下载链接和未核实事项必须完整。文件上传失败继续交付原答复，不展开文件全文。模型表达仍需真实会话验证，执行器终态和宿主汇总都不独立证明业务成功。

## 当前群历史查询工具

`feishu_group_history` 从 agent-worker 迁入本插件，供 Main 按需补充任务上下文。它只向可信飞书群会话注册，接受可选 `limit`（1–50，默认 50），不接受群 ID、账号或任意查询路径。使用当前机器人账号的 SDK 客户端，遵循该账号的群读取策略及 `tools.chat` 开关；不会回退到用户身份。权限失败明确返回错误，不当作空历史。返回最近消息及是否仍有更多消息，不自动遍历群历史。

agent-worker 的旧 history/Lark CLI 配置仅为加载兼容保留，不再控制这个工具。迁移保留工具名，Main 的工具白名单无需改名；若白名单只允许 `plugin:agent-worker`，需改为允许 Feishu 插件或显式允许 `feishu_group_history`。Worker 与 Main 的暂停问答通信尚未实现，缺少上下文仍由 Main 补充后继续原 topic。

### Worker 结构化补充与交互卡片

Worker 的 `context_request` 可携带 `fields`（最多 6 项）、`allowFreeText` 和仅供参考的 `recommendation`。Main 优先根据原任务、明确会话上下文和适用规则自动 `reply`，必要时在原授权内查询补齐；推荐答案不能当作用户已选择。`reply.answerBasis` 可记录简短依据来源，不记录内部推理。需要用户选择时调用 `await_user`，可传 `knownValues`，只渲染未确定的字段。旧版纯文字提问继续兼容。若所有字段已确定且禁用自由文本，Main 应直接 reply，不渲染无回答入口的卡片。续接工作卡在图片上传等发送前步骤失败时允许重试；消息发送结果不明时保留尝试标记，避免重复卡片。

字段支持 `text`、`number`（可指定 min/max）、`single_select`、`multi_select`、`date`、`date_range`、`datetime`；选择项为 `{label,value}`，日期类必须指定 IANA `timezone`。日期范围包含结束日期；日期时间保留飞书回传的明确时区偏移；没有偏移时按字段声明时区解释。选项不默认预选。少量单选可直接点击按钮；表单修改不恢复任务，点击“确认并继续”才提交；“取消任务”独立于表单校验，并需用户确认。

例如 Worker 可返回：

```json
{"type":"context_request","question":"请确认核查范围","reason":"日期和环境尚未明确","progress":"已确认只读核查方式","fields":[{"id":"environment","label":"环境","type":"single_select","required":true,"options":[{"label":"生产环境","value":"production"},{"label":"测试环境","value":"test"}]},{"id":"period","label":"录音日期范围","type":"date_range","required":true,"timezone":"Asia/Shanghai"}],"allowFreeText":true}
```

只有进入 `awaiting_user` 才将工作卡替换成交互卡，收起工作 GIF。优先更新该任务当前绑定的工作卡，在同一条消息上显示选择、日期或输入控件；只有任务尚未绑定卡片时才接管当前 Main 轮次的工作卡。Main 其他轮次的卡片不能接管已有任务。仅在没有独立工作卡且原卡被多个任务共享时另发问题卡，不覆盖其他 job。工具返回 `presentation.interactive=true` 时，卡片本身就是提问，Main 结束当前轮次，不重复发送投递确认或问题正文。宿主将当前轮次标记为等待用户，不因 Main 回复结束发送“完成了”等成功提醒，也不以确认文字覆盖交互卡。无卡片绑定、字段不支持、卡片超限或发送失败时使用文字提问，同样不发送完成提醒。

每轮交互提问卡片投递成功后，向原提问者发送一次应用内加急，不另发消息、不使用短信或电话。`workingCard.questionUrgentApp` 默认开启，可在设置关闭（支持账号覆盖）；需要飞书 `im:message.urgent` 权限及群加急策略允许。加急尝试持久化，重复事件、并发和重启不重复加急；加急失败不影响问答，记录错误供管理员核查。Main 自动补充、已回答或过期问题不加急。

回调核验真实操作人、账号、群、消息、问题期限以及原任务授权。表单字段按服务端保存的问题验证；未知字段、覆盖 Main 已知字段、非法选项、无效日期和颠倒范围均拒绝。校验失败通过回复提示，保留客户端已填写内容。补充说明作为参考数据，不扩大授权。仍可直接回复卡片；多个待回答任务无法明确定位时由 Main 澄清，不自行选择。

答案先保存到宿主状态目录内的 `feishu-worker-questions/questions.sqlite`（权限 0600），再异步交回所属 Main 的同一个 FIFO，不让飞书回调等待模型执行。提交后卡片 A 保留问题与选择的答案，回复 A 创建仅显示干活中 GIF 的卡片 B；恢复执行事件只更新内部进度，不将 GIF 替换为文字确认卡；Main `reply` 后恢复原 job、原 Worker 会话和执行约束，不另发续接确认消息。B 承接进度，下一次提问原地更新 B，提交后再创建下一张工作卡。最终结果只更新最后一张工作卡，并在任务成功完成后 @ 原对话者提醒；旧问题卡保留问题与答案。结构化字段通过受信任桥接保存到 job 的 `questions[].answerValues`，并传入 `mainReplies`，侧边栏任务过程显示“用户 · 卡片选择”或“Main · 自动补充”，原始 JSON 保留来源和字段。

Main 自动补充也使用同一续接机制：原卡保留问题与实际补充内容，并标记“Main 自动补充”，随后新建仅显示干活中 GIF 的工作卡，继续绑定原 job。共享工作卡时另建补充记录，不覆盖其他任务。自动回复、超时扫描和启动恢复按同一问题串行处理，在读取状态和发送工作卡前去重。发送成功先保存消息回执，再绑定原任务；绑定失败时将已知的未绑定工作卡改为状态提示，收尾失败保留待处理记录供恢复重试，不重发卡片、不重新执行业务。重复恢复事件复用已创建的工作卡；发送结果不明时保留尝试标记，不自动重发。长补充在卡片中展示摘录，完整内容保留在任务与补充记录；历史卡更新失败不阻断工作卡续接。明确未发送的失败可通过同一答案的幂等 reply 或服务启动恢复卡片，不重跑业务任务。恢复前核对原授权、任务状态、问题期限与最新问题；已结束任务及旧问题不补建工作卡。

提交去重使用持久化问题状态；并发回调只启动一次续接。失败保留答案，提供显式“重试交回 Main”；重启时恢复提交卡的重试入口，不自动重放不确定的 Main 轮次或卡片创建。创建续接卡结果不确定时不重复创建，需核查实际消息。旧轮次、其他用户和已结束任务不能重复操作；等待阶段不占 Worker 执行并发槽位，不发送成功提醒。真实桌面/移动端控件渲染、回调权限及模型自动补齐效果仍需部署后验收。

旧兼容入口的 Agent Repo 布局支持：workspaceSync.root 为角色仓库，submodules=[]；可配置 project={path:"project",expectedUrl:"登记远端",branch:"main",remote:"origin",submodules:[{name:"wiki",path:"wiki"}]}。project 必须是该角色仓库下真实独立 Git 根目录，禁止外部软链接、Git Submodule及远端不匹配。分别同步角色、项目和显式项目子模块；组合 skillDirectories=["skills","project/.agents/skills"] 的版本发布给 worker，主会话 workspace 应匹配 root。未配置 project 保持单仓行为；迁移前先初始化子模块，不在对话中自动克隆。

旧兼容入口的 Agent Repo 双仓布局可配置 workspaceSync.preserveLocalMemory=true（并关闭 includeUpstream）：未暂存的 MEMORY.md 与 memory/YYYY-MM-DD.md 在不重叠的快进中保持原样，不自动提交。远端同路径变更、暂存项、非原生记忆修改或异常路径仍阻止同步。此例外只作用于配置独立 project 的 Agent 根，不能用于 Project Repo 或 wiki。

外部插件的 before_prompt_build 会话钩子需要 plugins.entries.feishu-conversation.hooks.allowConversationAccess=true；否则宿主会阻止上下文注入并给出 diagnostic。安装能力授权与此配置权限分别核对。新用户三插件接入见 [模板操作步骤](https://github.com/Lydanne/agent-repo-template/blob/main/docs/openclaw.md)。

### Agent Repo 人员资料

安装配套 agent-repo 插件且当前 Agent 已绑定时，已接纳的人类消息会更新该 Agent 的本地人员目录，包含真实发送者及本轮原生提及的同事。复用账号/应用隔离的通讯录缓存；企业邮箱优先 enterprise_email，缺省时取 user.email。无通讯录权限时保留事件姓名和 OpenID，未取得的邮箱或部门不猜测。未安装配套插件时继续原有行为。

Agent Repo 消息侧边栏可查看、更正或删除这些资料。该通讯录与 colleagueProfile 的个人角色/回复偏好独立，不能以“删除我的画像”清除通讯录，也不把通讯录资料当成权限。Gitea 邮箱前缀仅是候选。当前任务的人员快照传入 SourceTask 和后台任务，Issue 代录由项目技能执行：提问人是 recorder，“记录给 @某人”的明确被提及人是 Assignees；不替换原生 Gitea 创建者。

### 群成员资料同步

配套 `agent-repo` 的人员资料窗口提供当前群同步按钮。Feishu 使用应用身份分页读取成员并获取通讯录资料，按可信群路由写入对应 Agent 的本地人员库。默认开启入群自动同步；可用账号配置 `peopleSyncOnJoin: false` 关闭。自动触发需在应用后台订阅 `im.chat.member.bot.added_v1`（机器人入群）和 `im.chat.member.user.added_v1`（用户入群），仅部署处理器不代表平台已经订阅。机器人入群启动全量同步，用户入群只处理新成员；不发送欢迎或同步通知。配置中的群访问策略和 Agent 绑定仍生效。


普通单条私聊正文直接展示 `[Request: 当前消息]` 下的用户内容，不再加姓名或 OpenID 前缀。没有引用、线程或撤回时，消息 ID 仅在 `[Metadata: 任务来源]` 的 sourceMessageIds 中出现一次，省略重复的“消息 ID”块和无参考内容可区分时的固定来源说明。群聊、引用/线程、多来源和撤回场景保留来源规则及各自处理协议；消息 ID、真实发送者、人员采集、source lease 和撤回追踪仍由渠道在原生上下文和存储中维护，不从精简正文推导权限。

### 完成报告入口

后台结果正文已有报告链接时，完成提醒只保留原生 @ 和提醒文案；正文未包含报告入口时，插件将可用的完整报告链接放在完成提醒末尾。没有独立提醒或结果需要分段发送时，入口保留在结果中。提醒发送失败时尝试恢复卡片内入口；后台文档上传及重启恢复沿用已选位置，避免重新插入重复链接。普通聊天和没有可用报告的任务不追加链接。

完成提醒使用卡片发送，原生 @、老师称呼、提醒正文及可选报告链接放在同一个 Markdown 元素内，不在 @ 后插入换行；窄屏由飞书自然折行。

### 定时请求的跨插件运行上下文

agent-repo 的原生时钟回调通过桥接进入飞书时，定时投递使用宿主公开的 `lifecycle.runInBackgroundContext` 进入飞书插件实例，再创建来源任务、交给 Main。不能直接沿用调用方的实例上下文：新宿主的命名运行时存储按插件实例隔离，会在来源创建阶段报 `Feishu runtime not initialized`。旧宿主未提供该生命周期接口时保留原兼容路径。失败阶段与错误摘要保存在私有调度记录中，未知结果不自动重放；管理员核对 Main、来源任务和 Worker 均未接纳后才可恢复补跑。

定时群消息整理和每日清单由 Main 直接读取原群历史、核对已有任务状态并汇总，不委派 Worker 做整理；新增业务执行仍遵守角色边界。定时最终结果使用 2.0 卡片和 Markdown 表格，检查卡片体积及表格数量限制，记录真实消息回执。日程接纳、Main 完成和消息送达分别核对，不以没有 Worker jobId 判定整理失败。

Main 返回的 `isError`、`isStatusNotice` 及宿主标准失败文案（含 `couldn't finish this reply`）不能作为 Worker 正式报告：不更新结果卡、不写入待发送正文、不确认交付回执。原任务和报告保留，按现有交付状态处理重试；不会因此重新执行 Worker 业务。


### Worker 超时后的重新补充

超时继续后，原问题卡显示“重新补充”。原请求人点击后得到新的补充卡，旧按钮移除；重复回调复用同一记录。补充提交由宿主直接送入对应 Worker 的接续入口，不等待 Main 的消息 FIFO。当前 exec 运行轮无法实时注入，答案先持久化，轮次结束后接续；最终结果仍由 Main 核验交付。卡片发送结果不确定时保留现场，不盲目重复发送。来源、请求人、群、账号、问题有效期及撤回检查仍生效。

Main 接收 AgentWorkerObservation 过程记录，包含超时续接、结构化本地查询和补充接收/派发。具体字段与时序见 [Main/Worker 协作协议](../../docs/main-worker-collaboration.md)。

补充无法接续时，`supplement_unavailable` 将原补充卡更新为“补充未执行”并说明失败、超时、取消或会话缺失原因，保留用户补充。卡片更新失败保留待更新状态，由 Worker 持久化过程事件重试；过了问题提交期限仍可更新已受理补充的结果。来源失效时不再向原渠道发送。

## 宿主拦截错误发送诊断

发送形如 `Your message could not be sent: … (blocked by plugin)` 的宿主拦截提示时，输出 `feishu: host-error-delivery` 的 attempt/acknowledged 关联记录，包含进程、调用文件位置、正文与目标的哈希、回复绑定状态及成功后的平台消息 ID。日志不记录提示正文、账号或收件人原值、凭证及完整文件路径。诊断不拦截、不重试、不改变发送结果；日志失败也不能使已发送消息被重发。此记录用于区分新拦截与历史通知重复发送，本身不代表已修复发送来源。

纯 SQL 批次超过 `maxFiles`（默认 20）时，最多接收 200 个不同源文件；逐个沿用媒体读取权限、单文件及总大小限制，全部原文按文件名收录文档，并合并为一份 `sql-sources.md` 原文附件。代码围栏会避让 SQL 中的反引号，重复路径去重；不执行 SQL。汇总附件仍受单文件预算约束，正文转换失败时保留汇总原文附件。混合类型文件继续遵守原数量限制，数量及 SQL 编码、汇总大小等失败有明确诊断码；不静默丢弃超限文件。

### 同群成员补充 Worker 任务

其他同群成员通过 Main 给已有 Worker 问题补充线索时，先保存补充，再给原请求人发送授权卡片：**允许一次 / 一直允许 / 允许这轮（Worker）**。只有原请求人本人可点击；一次许可仅放行当前补充，Worker 许可仅当前任务，长期许可仅同账号、同群、同一 Agent 下该同事补充该请求人任务的组合。没有确认不恢复任务，其他成员不能借补充替原请求人决策、授权业务写入或取消任务。许可与补充来源分别校验并持久化，重复回调不重复恢复；若已超时继续执行，获准补充排队等待当前轮结束后沿原会话接续。

定时计划支持 `deliveryMode=source/group/thread`：默认保持原位置；group 在原群主会话发新消息（不带原话题回复目标）；thread 只允许原请求已知话题。授权来源、原群、请求人和 Main 执行会话保持绑定。投递位置写入每次执行及 Worker 来源快照，覆盖 Main 最终卡片、Worker 完成结果和后续提问；不通过变更位置把原请求正文改成新授权，不影响已在途任务。缺少字段的旧计划行为不变。管理 API 及示例见 agent-repo README 的“群内管理 API”。

### 飞书组织与全部部门同步

`feishu-organization-sync` 通过 AgentRepo 图服务保存实际组织、完整部门目录和组织归属/父子关系。首次没有同步回执时后台初始化；管理员可在 AgentRepo 实体页选择当前 Agent 绑定的账号，明确发起“同步飞书组织与全部部门”。从根部门 0 分页、逐级遍历，不依赖机器人见过的联系人。组织信息需要 tenant:tenant:readonly，根目录查询需要全员通讯录范围及相应部门读取权限；不足时展示 partial/failed 和实际所需权限，不伪造组织、不清理关系。完整快照仅维护部门的组织关系，保留人员关系及人工更正。状态持久保存在 AgentRepo 统一库，刷新不重新执行，未知回执不自动重放。不新增周期计划，不自动变更飞书权限或发送消息。详细协议见 [实体图](../../docs/entity-library.md)。

### 组织与部门持续同步

飞书插件通过统一 AgentRepo 来源能力主动维护目录：部门事件合并 10 秒后局部刷新，层级变化或大量变化合并为全量；组织每小时、完整部门目录每 6 小时校准。默认启用，可通过账号继承配置 `directorySync` 调整 `enabled`、`organizationIntervalMinutes`、`fullIntervalMinutes`、`eventDebounceSeconds`。配置并发布 `contact.department.created_v3`、`contact.department.updated_v3`、`contact.department.deleted_v3` 事件订阅后才有实时事件触发；未收到事件时管理页显示订阅待验证，周期校准仍工作。

持久队列、执行租约和同步回执统一保存在 agent_repo.sqlite。来源写入串行，同账号目录请求并发最多 2；失败退避、重启恢复。完整目录中未发现部门仅进入待核验，不自动断联；可信删除证据核验通过后结束该部门组织层级关系，保留人员关系与历史。详情见 docs/entity-library.md。
